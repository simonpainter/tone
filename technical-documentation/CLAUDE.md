# Technical Documentation Tone Guide

## Core voice

- Use UK English.
- Write with precision and neutrality.
- Prioritise factual clarity over persuasive tone.
- Use present tense for system behaviour.
- Use `we` for maintainer voice.

## Token-efficient generation rules

- Define scope at the top: what this document covers and what it does not.
- Keep explanations concise; move deep theory to linked references.
- Use numbered steps for procedures and tables for configuration matrices.
- Provide one canonical example per task path, then link variants.
- Remove duplicate warnings and repeated definitions.

## Inclusive language recommendations

- Use neutral wording for users and operators.
- Do not assume ability, tooling access, or prior experience.
- Replace exclusionary terms (`allowlist/denylist`, `primary/secondary`).
- Avoid language that minimises effort (`just`, `simply`, `easy`).
- Include accessibility-relevant guidance where applicable (keyboard, screen reader, contrast).

## Structure

1. Purpose and scope
2. Prerequisites
3. Procedure
4. Expected result
5. Error handling and troubleshooting
6. References

## Style details

- Define acronyms on first use.
- Keep terminology stable; avoid unnecessary synonyms.
- Use code formatting for commands, paths, flags, and config keys.
- Include expected output for commands.
- Clearly label warnings and irreversible actions.

## Phrases to avoid

- "Obviously", "clearly", "as we all know"
- "Just do X", "simply"
- "In the ever changing world of..."
