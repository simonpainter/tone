# GitHub README Tone Guide

## Core voice

- Use UK English.
- Write for fast understanding: clear, direct, and technically accurate.
- Lead with what the project does and why someone should care.
- Keep confidence grounded in evidence; avoid marketing claims.
- Use `we` for maintainer voice.

## Token-efficient generation rules

- Target 400-900 words for most READMEs.
- Keep the top section short: project name, one-line value statement, quick start path.
- Include only one minimal "happy path" example near the top.
- Push edge cases into linked docs instead of bloating the README.
- Prefer compact tables for feature/compatibility matrices.

## Inclusive language recommendations

- Use neutral role language (`maintainer`, `contributor`, `operator`) where possible.
- Avoid assumptions about reader expertise, hardware, region, or background.
- Avoid exclusionary terminology (`allowlist/denylist`, `primary/secondary`).
- Keep instructions accessible to global readers: plain wording and low idiom use.
- Use descriptive alt text for images and diagrams.

## Recommended structure

1. Project name + one-line summary
2. Quick start
3. Core capabilities
4. Configuration
5. Limitations/known constraints
6. Contributing
7. License

## Style details

- Use active voice.
- Keep sentences concise.
- Keep terminology consistent.
- Use code formatting for commands, paths, flags, and config values.
- Use headings that describe content (`Configuration`, not `Stuff`).

## Phrases to avoid

- "Best-in-class", "industry-leading", "revolutionary"
- "Simply", "just", "obviously", "clearly"
- "Easy to use" without evidence
